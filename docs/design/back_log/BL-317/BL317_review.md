## ⚠️ 実装前に修正すべき指摘

### A.【最重要】ウィンドウ対象がraw行で、表示側フィルタと乖離する（§15.1該当）

`_select_relevant_agreements`は**Superseded / Directive を含むraw行**に対してwindow=40を適用しますが、その後`_build_agreements_context`（10473-10479行）がSuperseded・Directiveを除去してから表示します。実DBの直近40件の構成を数えたところ：

```
直近40 raw行 → 表示対象（非Superseded D/D）はわずか23件
（内訳: Superseded 14、Directive 12、Rejected 11 …）
```

つまり「直近40件」と書いても**実効窓は約23件**で、しかもSupersedeがバースト的に起きるターンでは実効窓がさらに縮みます。「表示する行集合」に対して窓を敷くべきです。かつ、D/D非Superseded述語が `_build_agreements_context` と `_select_relevant_agreements` の**2箇所に重複**すると、これはBL-207/D-163と同型のドリフト事故の温床です。**述語を共有ヘルパーに抽出し、選択側もそれを使う**形に修正してください（AGENTS.md §15.1・§15.3）。テスト計画にも「窓境界にSuperseded/Directiveが混在するケース」を追加が必要です。

### B. プロンプトキャッシュ影響の記述が楽観的すぎる（§16.3）

「現状よりキャッシュ効率が悪化する理由はない」は正確ではありません。現状のagreements_textはrowid順**append-only**で、ターン間でプレフィックスが安定します（in-placeのstatus更新で崩れることはあるが）。フィルタ導入後は**タスク遷移のたびに relevant集合が作り変わり、ブロック全体が再構築**されてプレフィックスキャッシュがその位置から全崩れします。タスク内では安定するのでトータルでは軽微と予想されますが、設計書には「タスク遷移時にキャッシュを一度壊すコストを認める」と正直に書き、宿題（実測確認）に**キャッシュヒット率の確認**を追加することを推奨します。BL-312の教訓を引用した箇所だけに、ここ雑なままだと同じ失敗を繰り返します。

### C. depends_on呼び出しパターンの防御が既存コードより弱い（§13.1）

提案パターンは `_get_current_task(state).get("depends_on", [])` ですが、既存の12697行は防御付きです：

```python
_current_task_depends_on = [d for d in (current_task.get("depends_on", []) or []) if d]
```

`depends_on`が万が一JSON**文字列**（agreementsテーブルはJSON textで保存、4032行参照）として来た場合、`set(task_depends_on)`は**文字1字1字に分解されて静かに破綻**します。5箇所すべてを12697と同じ `(… or [])`＋`if d` 付きに統一してください。現状の5呼び出し箇所はstate内のtask plan（list）を参照するので実害の可能性は低いですが、§13.2の原則「フォールバックは消費経路を確認してから」に照らして設計書に明記すべきです。

### D. current_task_id誤解決時に「それっぽい誤り」が静かに選ばれる（§13.2 問3）

`current_task_id`が`current_phase`のタスク一覧に無い場合（再計画後のドリフト、BL-190）、`_get_current_task`は**tasks[0]へフォールバック**します。既存挙動ですが、今回この値が**コンテキスト絞り込みの駆動**に昇格するため、誤解決時に「間違ったタスクの関連集合＋窓」が静かに選ばれます（plausible-but-worst）。検知手段は⚠️警告ログのみなので、設計書の「既知の限界」節にこの劣化モードを追記してください。

### E. 15181-15184行のBL-103コメントが陳腐化する（§6）

「Expert側の窓付きhydrate_contextと**非対称かつ長時間runで際限なく肥大化するリスク**」というコメントは、この変更で嘘になります。同一PR内で更新することをタスクに明記してください。

## 💡 推奨（任意だが効果大）

- **F. 5箇所の3行パターンを1ヘルパーへ**（例: `_build_agreements_context_for_state(conn, state)`）。「パターンを統一する」はD-179（ツール役割記載の1箇所だけ漏れ）と同じ失敗クラスです。ヘルパー化なら追加呼び出し箇所ができても取りこぼせません。
- **G. 定数40はAppconfigへ**。decisions側は`config["expert_history_window"]`（Appconfigフィールド）です。対称性と§15.1の観点で、`Appconfig`フィールド＋既定40の方が一貫します（§7承認対象は変わらず）。
- **H. 「重複排除テスト」は成立不能**。relevant集合とothers集合は定義上**分割（disjoint）**なので両方に該当するagreementは存在し得ません。このテストは常にpassする空振りテストです。A対応の境界テストに置き換えることを推奨。

## 🔍 Nit（事実修正）

- **I.** 「517件中373件の非Superseded」の373は**Directive込み**の数です。実際にプロンプトへ表示されるのは**301件**（Directiveは10478行で除外済み）。設計書の数値を正確に（137k文字の実測値自体は正しいので影響小）。
- **J.** 疑似タスクid（`plan_review` / `macro_audit_round34` / `goal_revision_review` / `task_user_audit_r19`、計5行）は`depends_on`に現れ得ないため常に窓落ちします。実害は小さいですが「既知の限界」に1行追記推奨。
- **K.** `keep_ids`を`a["id"]`で照合していますが、BL-311でid枝番の自己修復が必要だった経歴があるため、id重複があれば意図より多く残る可能性があります（無害方向）。rowindexベースでも同等です。任意。

## 総評

**方向性は正しく、実測に裏打ちされた良い設計です。** 行番号・既存ヘルパー・テスト前提・frozen=0の事実はすべて検証で裏付けが取れ、削減効果の試算も現実的です。ただし **A（窓と表示フィルタの述語分離＝§15.1違反の芽）はマージ前必須修正**、B〜Eも設計書へ反映すべきです。特にBはBL-312を引用しながら逆の結論を楽観記述している点で、§16.3（報告の正直さ）の観点から要修正です。

Planモードのため編集は行っていません。このレビュー内容を`docs/design/back_log/BL-317/BL317_basic_design.md`へ反映する場合はActモードに切り替えてご指示ください。

## 対応結果

すべての指摘を実コード・実DBで検証の上、採用した（詳細は`BL317_basic_design.md`）。

- **A**: `_is_agreement_displayable`を共有述語として抽出し、`_build_agreements_context`と
  `_select_relevant_agreements`の両方から使うよう修正。windowは「表示対象」に絞り込んだ後の
  直近N件を指すよう変更。実測値（直近40 raw行→表示対象23件）で裏付けを確認。
- **B**: プロンプトキャッシュへの影響の記述を「悪化しない」から「タスク遷移時にプレフィックス
  キャッシュが崩れることを認める」へ修正し、宿題にキャッシュヒット率の実測確認を追加。
- **C**: 共有ヘルパー`_task_depends_on`を新設し、既存の12697行・新規5箇所すべてで統一。
  `task_id=""`のagreement行（BL-318のデータ是正で実際に作成済み）との衝突リスクを回避。
- **D**: 「既知の限界」節に、`current_task_id`誤解決時の劣化モードを明記。
- **E**: 15181-15184行のBL-103コメントの更新をCritical Filesに明記。
- **F**: `_build_agreements_context_for_state`ヘルパーを新設し、5箇所すべてで統一。
- **G**: 定数をモジュール定数からAppconfigフィールド（`agreements_context_recency_window`、
  既定40）へ変更し、`expert_history_window`との対称性を確保。
- **H**: 「重複排除テスト」を削除し、A対応の境界テスト（Superseded/Directive混在時に
  実効窓が正しく機能すること）へ置き換え。
- **I**: Context節の数値を373→301（実際に表示される件数）へ訂正。
- **J**: 「既知の限界」節に疑似task_idの扱いを追記。
- **K**: 低優先度・無害方向のため見送り。
