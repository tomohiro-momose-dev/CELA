# BL-287: ツール呼び出し引数の完全一致反復の専用検知（訂正ナッジ→無効なら強制終了）

> **[事後再構成についての注記]** 本ドキュメントは、BL-287の実装が完了・コミット（`f969a0b`）済みの後になって、AGENTS.md §7（BL-scoped plansはdocs/design/back_log/BL-xxx/へ保存）の遵守漏れが発覚したために書かれた**事後再構成版**です。Plan Mode実行時に実際に生成・承認された元の設計文書そのものではありません（元ファイルはClaude Code側の一時ファイル`~/.claude/plans/`に書かれていましたが、以後のPlan Modeセッションで上書きされ、セッション内の生トランスクリプトから逐語的に復元するのも実務上のコストに見合わないため断念しました——ユーザー承認済み）。内容は`docs/design/back_log/issue_backlog.md`のBL-287詳細記録と、実装済みコード（`cela_main.py`、コミット`f969a0b`）を突き合わせて再構成したもので、事実関係はそちらを一次情報源とします。

## Context

ユーザー依頼のログレビュー（`log/2026-08-27/1634`）で、Expert（地域公共交通需要推計・交通統計分析専門家）がtask_1_2で4回連続BL-231ループガードにより強制終了・有効出力ゼロという事態を起こしていたことが判明した。同日実施したBL-231閾値変更（3→10）が想定していた「言い回しの言い直し」ではなく、同一のweb_search検索クエリを8回連続でそのまま繰り返すという正真正銘の生成崩壊だった。閾値10への引き上げはこのケースを一切救えず、むしろ1回の崩壊検知までに16イテレーションかかるようになり、同じ崩壊が4回連続発生（BL-033フェイルクローズで全て失敗）、この4回だけでrun全体のweb_search呼び出し80回中59回（74%）を空費した。

ユーザーからの指摘「同一クエリの反復が真の生成崩壊なのか、目当ての情報が見つからず律儀に再試行しているだけなのかは分からないのでは」に対し、web_search等の外部APIはほぼ決定論的なため、原因がどちらであれ同一引数の再呼び出しは新しい情報を一切生まないという結論は変わらないと判断し、「真の崩壊か否か」の判別は不要とした。

## 設計調査で確定した事実

`_bl231_plan_sig`（ツール名＋正規化引数のソート済み署名）は既存のBL-231検知（`_bl231_combined_hash`＝テキスト＋`_bl231_plan_sig`の結合ハッシュ）の一部として既に計算されている。ツールループは`tool_calls`が空の応答で即座に正常終了するため、反復ウィンドウにカウントされる全iterationは必ず`tool_calls`を持つ。したがって`combined_hash`がN回連続一致するなら、その部分文字列である`plan_sig`も必ずN回連続一致する——新検知の閾値（3）は既存閾値（10）より小さいため、新検知は既存検知よりも常に先に発火する（数学的に優越する）。既存のBL-231コードは削除・変更せず、万一の保険としてそのまま残す。

## 設計・実装内容

新規定数`_TOOL_CALL_REPEAT_NUDGE_THRESHOLD = 3`（`cela_main.py:5816`）を追加。`_query_AI_live`内、既存BL-231検知の直前に新検知ブロックを追加した。

- 直前iterationの`tool_calls`から`_bl231_plan_sig`（既存ヘルパー、変更なし）を計算し、直近`_TOOL_CALL_REPEAT_NUDGE_THRESHOLD`件のスライディングウィンドウ（`_recent_tool_plan_sigs`）で管理する。
- ウィンドウ内が全て同一署名（`len(set(...)) == 1`）になった時点で「ツール呼び出し引数の完全一致反復」と判定する。
- 1回目の検知時: 訂正メッセージ（「同一引数を再送しても新しい情報は得られません。別の切り口で検索し直すか、仮定を置いて先へ進んでください」）をループへ注入し、1回だけ自己修復の機会を与える（BL-016/BL-056bの「残りiter数警告」と同じ、ループを壊さずシステムメッセージを注入するパターン）。フラグ`_tool_repeat_nudge_used`で1回のみに制限する（BL-283の1回差し戻しポリシーと同型）。
- ナッジ後も同一引数の反復が続いた場合のみ強制終了する。スライディングウィンドウの性質上、ナッジ直後に同じ署名が続けば次の1回（合計4回目のツール呼び出し）で即座に終了する（新しい署名に切り替わった場合は、そこから改めて3回連続一致するまで猶予がある）。
- ツールディスパッチループ本体・既存BL-231ロジックは無改修。`_LAST_REPETITION_GUARD_TRIPPED`（観測用グローバル、下流の意思決定には使われない）に`"trigger": "tool_call_repeat_after_nudge"`を追加した。

## 検討したが見送った代替案

- 3回目のツール呼び出し自体をスキップしキャッシュ結果を返す方式: ディスパッチループのtool_call_id処理に手を入れる必要があり、`_query_AI_live`の最もセンシティブな箇所への変更リスクが増えるため見送り、1回分の無駄なAPI呼び出しは許容することにした。
- 既存の`_LOOP_GUARD_REPETITION_WINDOW`ロジックの置き換え・削除: 数学的には到達不能になるが、万一新ロジックに見落としがあった場合の保険として残す方が安全と判断。
- ナッジを複数回（例: 2回）許容する案: BL-283の「1回差し戻し→検証→確定」という単純な二段構成の前例に倣い、1回のみとした。
