# BL-197 調査記録：User AIの承認・指示が、タスクのacceptance_criteriaを超える手段・検証水準を後付けで積み増す

> 正式なPlan Modeセッションではなく、ユーザーからの繰り返しの「まだ直っていません」報告を
> 契機とした3段階の実ログ調査（Explore/直接読解の反復）。同一症状（GIS実測要求）に対し
> 3回連続で異なる真因を特定するに至った過程そのものが再発防止上の教訓であるため、
> 診断の変遷を圧縮せずに記録する。関連: [BL-196](../BL-196/BL196_investigation.md)、
> [BL-198](../BL-198/BL198_basic_design.md)、`docs/design/decision_lineage.md` 論点145。

## 発端

BL-195でゴール文を実データ化（長野県茅野市）した直後の初回ドライラン
（`log/2026-08-09/1230`）で、`task_1_1`がホワイトボードVer.19・round 16まで進んでも
承認に至らず空転しているのをユーザーが発見し、レビューを依頼した
（「1230のログをレビュー 何か困っている点はないか？」）。

## 第1の診断（誤り・BL-196として実装）

ログ1230を読解した結果、acceptance_criteriaが実質的に「OSM PBFファイルからの区間別標高・
冬季リスクの実測抽出」に相当する水準を要求しているように見え、Expertの実行環境
（`python_repl`は`math`/`statistics`等の許可リストのみのサンドボックスでPBFのデコードに
必要な`zlib`/`struct`もファイルI/Oも禁止、`web_fetch`も`text/*`と`application/pdf`のみ
対応）ではこれが原理的に達成不能である、と診断した。

この診断に基づき`call_task_planner`のプロンプトに項目13（実行環境に無い専用処理能力を
acceptance_criteriaへ要求しない旨のガードレール）を追加し、BL-196として実装した。
ユーザーからは「acceptance_criteriaは、公的統計＋ゴール文の与件＋合理的な工学的仮定
（その旨明記）で満たせる水準にとどめ、の記述は、地理やGISなど、ゴールの特化した記述は
排し、一般的な言葉で書いてください」という明示的な訂正指示を受け、当初のGIS/OSM PBF
特化の文言をドメイン非依存の一般的表現へ書き直した。

## 第2の診断（誤り・部分的にBL-197として実装）

BL-196実装後の再開ラン（`log/2026-08-09/1718`）で、ユーザーが「1718ログ うーんやはり、
gis実測を送球してきます」と再発を報告。再調査の結果、**真因はtask_plannerではなく
User AI自身**であることが判明した。`task_1_1`のacceptance_criteria自体は「地図ベースで
整理」程度の妥当な記述であり、PBF直接抽出までは要求していなかった。実際の経緯：

1. Expertが公開情報＋合理的仮定に基づく成果物を提出
2. User AIのStage2（issue確認）が「実測成果物が未提出」として`write_issue(DEFER, task_1_2へ)`
   を実行——ここまでは正常なtriage
3. **同じターンのStage3（統合承認判断）が、そのDEFERを無視して`approval_status="Rejected"`
   を返す**（`log/2026-08-09/1230/log_no_prompt.md:27838`）
4. Stage4が「発注者への照会で作業を停止することは認めない」とし、Geofabrik配布のOSM PBF
   ファイル・国土地理院標高タイル・OSMnx/osmium/QGISでの抽出・ファイルサイズ/ハッシュ値の
   記録までを具体的に義務付ける指示を出す（同ログ`27852-27929`）

ユーザーはこの発見に対し「なるほど うーん、いかにもAIらしい挙動です stage3は数値監査
なので、数字的なそもそもの信頼性を上げるために元情報を要求したのではと思います。これは
これで、監査層としてはよい仕事をしていますが、オーバーに振舞っていますね」と評価した。
この評価に沿い、**監査の厳格さ自体は否定せず、要求水準の上限だけを画す**方針を採った。

対応として、Stage3（既存の「🔥 発注者としての絶対的なスタンス」直後）とStage4
（差し戻し時の修正指示ブロック）の2箇所にガードレールを追加し、`log/2026-08-09/1733`
から再開した。

## 第3の診断（真因の完全特定・BL-197として実装完了）

再開後の`log/2026-08-09/1733`で、ユーザーが再度「1733ログ うーんやはり、gis実測を
送球してきます」と報告。ここで2つの独立した事実が判明した：

1. **DBとチェックポイントの不整合**：LangGraphのチェックポイント巻き戻し
   （`--resume`＋`--checkpoint-id`）は会話状態（`chat_history`・`phases`等）のみを
   戻し、`cela.db`側のホワイトボード・agreements・issue_log・verified_factsは
   **run_id単位で別管理のため巻き戻らない**。汚染された成果物を残したまま再開すると、
   `chat_history`が空でもUser AIがDB上の旧成果物を読んで同じ指示を再生産していた。
   ユーザー承認（「１を実行」）を得た上で、`cela.db`をバックアップしてから該当
   `task_1_1`行（whiteboard_drafts、agreements［`task_planner_phase_design`除く］、
   issue_log、verified_facts［`source_task_id='task_1_1'`］）を削除して再開した。
2. **非Stage4パスの見落とし**：初回ターン等、`chat_history`が空でStage3/4を通らない
   別の生成経路（`system_prompt_trailing`を用いる旧来のコードパス）が存在し、
   **初回ターンのUser AI自身が独力で「一次資料およびGIS実測に基づく初版成果物」を
   要求していた**。Stage3/4への修正だけではこの経路を通過してしまうため、
   BL-023「指示のスコープ」ブロックの直後に同趣旨のガードレールを追加する第3の
   パッチが必要だった。

DB清掃と非Stage4パスへの追加ガードレールの両方を適用した後、`log/2026-08-09/1744`から
再開した。

## 効果の検証（`log/2026-08-09/1744`）

再開前にBL-198の実装計画をExitPlanModeで一度提示したが、ユーザーが「実装前に1744の
ログを見て停滞の原因を調査」と指示し、BL-198着手より先にBL-197の効果を実ログで検証する
ことを要求した。調査の結果：

- User AIがTurn 1冒頭の思考ブロックにおいて「GIS実体ファイルや再実行ハッシュ等を今回の
  必須条件に追加する案」を`rejected`とし、理由を「現在タスクの受入条件を超える手段指定
  であり、BL-023/BL-197に反するため」と明示的に述べる挙動を確認した。
- Detectorも「情報不足自体をmajorの根拠にしない」ルールを一貫して適用していた。
- Reflectionも当該の足踏みを停滞ではなく正当なブロッキング依存関係と正しく判定していた。

この検証結果を受けてユーザーがBL-198（実測手段の供給）の実装を承認した。

## 副次的に判明した運用上の注意（恒久的な運用知識）

LangGraphのチェックポイント巻き戻しは会話状態のみを戻し、`cela.db`側の成果物は
run_id単位で別管理のため巻き戻らない。プロンプト修正後にドライランを再開する際は、
汚染された旧成果物が残っていないか（DB側）を確認し、必要なら該当task_id行をバックアップ
の上で明示的に削除してから再開する必要がある。

## 教訓（`decision_lineage.md` 論点145より）

1. 同一の症状（GIS実測要求）に対しAIは3回連続で異なる真因を推定し、そのうち最初の2回は
   不完全だった。ログの表層的な一致（「PBFという単語が出ている」）だけで原因を特定せず、
   誰がその要求を最初に発したかを発言主体まで遡って確認する必要があった。
2. ユーザーは3回とも「まだ直っていない」という事実だけを短く報告し、AIに再調査させた。
   原因の推定をAIへ委ねつつ結果だけを検証するこの進め方が、AI自身の誤診を3回とも
   捕捉した。
3. 抑止（BL-196/197）と供給（BL-198）は対の関係にあり、「実測できないものを要求しない」
   だけでは検索予算の浪費が残り、「実測できるものを与える」だけでは過剰要求が止まらない。
   ユーザーがAPI提供を提案したタイミングは、抑止側の効果が実証された直後であり、変数を
   一度に増やさない切り分けとしても適切だった。
