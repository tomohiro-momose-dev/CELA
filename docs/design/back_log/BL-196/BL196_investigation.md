# BL-196 調査記録：task_plannerが実行環境に無い専用処理能力を前提としたacceptance_criteriaを書いてしまう

> 正式なPlan Modeセッションではなく、ドライランログの直接読解による調査と即時実装。
> 後にBL-197の調査で「この診断は真因の一部にすぎなかった」ことが判明した経緯を含めて
> 記録する（診断の変遷そのものが教訓のため）。関連: [BL-195](../BL-195/BL195_investigation.md)、
> [BL-197](../BL-197/BL197_investigation.md)、`docs/design/decision_lineage.md` 論点145。

## 発端

BL-195のゴール実データ化後の初回ドライラン（`log/2026-08-09/1230`）で、`task_1_1`が
ホワイトボードVer.19・round 16まで進んでも承認に至らず空転しているのをユーザーが発見し、
「1230のログをレビュー 何か困っている点はないか？」とレビューを依頼した。

## 調査

ログを読解した結果、acceptance_criteriaが実質的に「OSM PBFファイルからの区間別標高・
冬季リスクの実測抽出」に相当する水準を要求しているように見えた。ユーザーから「検索、
ダウンロード可能な形式にPBFを含めれば、AIがPythonでデコードしてくれますか？」と
質問を受け、Expertの実行環境の制約を精査した：

- `python_repl`は`math`/`statistics`/`datetime`/`json`/`fractions`/`decimal`/
  `itertools`/`functools`/`collections`/`operator`/`re`のみを許可するASTベースの
  サンドボックス（`_ALLOWED_IMPORTS`）であり、PBFのデコードに必要な`zlib`
  （ブロブ展開）・`struct`（バイナリ解析）のimportは拒否され、`open()`によるファイル
  読み込みも`_DANGEROUS_NAMES`で禁止されている。
- `web_fetch`も`_ALLOWED_CONTENT_TYPE_PREFIXES = ("text/",)`と`application/pdf`のみ
  対応（`web_tools.py`）であり、バイナリ形式のPBFファイルはダウンロード自体を拒否する。

以上より、PBFファイルを「ダウンロード可能な形式で用意する」策では解決せず、そもそも
acceptance_criteriaがExpertの実行環境で原理的に達成不能な水準を要求していたこと自体が
問題である、と結論づけた。

これはユーザーが本来懸念していた「仮定の数値をこねくり回す帳尻合わせ」（BL-134/BL-194）
とは別種の問題であり、**達成不能な受入条件を課したことによる足踏み**と整理した。

ユーザーからは、実データ導入の狙い（「これまで仮定の数字で決めさせると制約への帳尻合わせ
的に、仮定や比率を変えてこねくり回す事を繰り返してきました。なので、実名地名と実際の
地理要件を入れて動かしてみています」）の共有があり、これを踏まえて「ストレステストを
増やす前にまずこの足踏みを解消すべき」という変数分離の方針で合意し、修正を進めた。

## 実装

`call_task_planner`のプロンプトへ項目13を追加した。

初稿はGIS/OSM PBFに特化した文言だったが、ユーザーから明示的な訂正指示を受けた：
「acceptance_criteriaは、公的統計＋ゴール文の与件＋合理的な工学的仮定（その旨明記）で
満たせる水準にとどめ、の記述は、地理やGISなど、ゴールの特化した記述は排し、一般的な
言葉で書いてください」。

この指示に沿い、最終的な文言はドメイン非依存の一般的表現へ書き直した：「専用の解析・
変換ツール、特殊形式のデータ処理、実測機器による現地計測などが無ければ原理的に満たせない
要求は、たとえそのドメインにおいて理想的な精度であっても課さない」「acceptance_criteriaは、
ゴール文で与えられた背景データ・web_searchで確認できる公的な二次情報・そこから導出した
合理的な仮定（仮定である旨を明記）の組み合わせで満たせる水準にする」「ゴール文に既にある
数値データ（人口統計等）で確立されている『実測値と計画仮定を分離して明記する』扱いを、
他の種類のデータにも同じ基準で適用する」。

具体的な追加文言・実装箇所は`docs/design/back_log/issue_backlog.md` BL-196セクションを
参照。

## この診断の限界（BL-197調査で判明）

BL-196実装後の再開ラン（`log/2026-08-09/1718`）でも同じGIS実測要求が再発したため
再調査したところ、**真因はtask_plannerではなくUser AI自身（Stage3/Stage4、および
非Stage4パス）であった**ことが判明した。`task_1_1`のacceptance_criteria自体は
「地図ベースで整理」程度の妥当な記述であり、PBF直接抽出までは要求していなかった。

BL-196自体はacceptance_criteriaの一般的な質を改善する施策として無効ではないが、
本件（GIS実測要求の空転）の直接の真因ではなかった。診断の変遷とその教訓は
[BL-197の調査記録](../BL-197/BL197_investigation.md)に記録している。
