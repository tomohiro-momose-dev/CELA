# BL-291/BL-292: 探索段階の固有名詞混入バイアス防止と、規模適合性（供給 vs 需要）の定量検証化（分野非依存の一般設計）

## Context

BL-278（Domain Reviewへの選定妥当性・十分性チェック追加、2026-08-26実装・commit `ce8b112`）が実運用でどう機能するかを確認するため、ユーザーが翌日のドライラン（`log/2026-08-27/1909`）を精査した。結果、BL-278の十分性チェックは「実装したのに全く働いていない」ことが判明し、ユーザー自身がその根本原因を2つの独立した欠陥として切り分け、`issue_backlog.md`にBL-291・BL-292として詳しく記録した（いずれも`open`・P1、「本線チャットでの設計検討事項」として複数の対応案を提示した上で判断を委ねる形式）。

**BL-291（探索段階の欠陥）**: task_2_1担当のExpertは、実際に検索する前の内部思考の時点で「イオン茅野店?」と自らの学習知識（事前知識）から商業施設名を連想し、その名前を最初のweb_searchクエリにそのまま含めた（`{"query": "茅野市 スーパー商業施設 大型店 イオン ザ・ビッグ 住所"}`）。ゴール文は「複数点在している」とのみ記載し特定ブランド名は一切挙げていないにもかかわらず、この1クエリの結果イオンタウン茅野1件のみが発見・登録され、以降の路線設計（task_2_2）も最終版までこの1件だけを前提に組まれた。BL-278のDomain Reviewは「成果物に複数候補比較の**痕跡**があるか」を見る設計のため、そもそも比較イベント自体が発生しなかった本件は捕捉対象外だった——これはBL-278のロジック上正しい挙動であり、レビュー段階の防波堤が原理的に無力な探索段階の問題である。

BL-291とBL-292は独立した欠陥（BL-291は探索の偏り、BL-292は判定基準の欠落）であり、どちらか一方の修正だけではもう一方は残る。両BLとも「求める対応」に複数の選択肢を提示し、AGENTS.md §16.1（軽量な案からの検討）を推奨した上でユーザーが判断を本線チャットに委ねている。

**[ユーザー指摘による設計拡張・1回目：上流ノードへの拡張]** 当初案はBL-292をDetector（Domain Review＋数値監査パス）とExpertの3箇所のみに閉じる設計だったが、ユーザーから「これは本来タスクプランナーやユーザーAI自体の出力・指示の監査にも言える。上流側で見逃してはいけない」との指摘を受けた。これはAGENTS.md §15.2（あらゆる経路を列挙せよ）そのものであり、同文書が引く先例（D-182：過度に厳格な受入基準がtask_planner・User AI・focus_guidanceの複数箇所から生まれ得るのに2箇所しか塞がなかった事例）の**逆方向版**にあたる——本件は「基準が緩すぎる」問題が、Detectorという下流の監査だけでなく、そもそも受入基準を書くtask_planner、レビュー・承認を行うUser AIという上流でも同様に見逃され得る。

**[ユーザー指摘による設計拡張・2回目：一般化＋独立層＋Reviewerへの拡張]** さらにユーザーから3点の指摘を受けた。

2. Detector・Reviewerには「十分性チェック」専用の独立した層（構造化されたJSONフィールド等）を置いてもよいのではないか。
3. 過去にBL-104のプロンプトキャッシュ設計で懸念していたトークン増量・キャッシュヒット率の問題は、実際には**モデル・プロバイダー依存**だったと判明した（当時使用していたdeepseek系はキャッシュヒット率が悪かったが、現在使用中のモデル・プロバイダーでは平均70%超のヒット率が出ており、当時ほどネックではない）。加えて、軽量・安価モデル（xxx-flash系等）は思考が浅く結論を急ぐよう設定されていることが多く、そうした挙動を補うのはプロンプト文言だけでなく**システム側の構造**（独立したJSONフィールドで明示的な回答を強制する等）であるべき、という指摘。

この3点を踏まえ、BL-292の設計を全面的に改訂した。「見送った代替案」に当初含めていた『新規JSONフィールドは追加しない』という判断は、上記③の新しい文脈（キャッシュ経済性の変化、軽量モデルの浅い思考への対策の必要性）により覆し、BL-266（`essence_sufficiency_concern`/`essence_sufficiency_reason`）と全く同じコードパターンで新規フィールドを追加する方針に転換した。以下は既存コードを実地に確認した上での、これら全ての指摘を反映した推奨設計。

## 設計

### BL-291: web_searchの最初のクエリへ「まず中立語で網羅」ガードレールを追加（軽量案・単独採用を推奨）

3つの選択肢（軽量案／機械的補完案／Detector独立探索の重量案）のうち、BL-291自身が「軽量・推奨」とする案1のみをMVPとして採用する。案2（構造的シグナルによる機械チェック）は「複数性を示唆する語」と「entityのカテゴリ」の対応付けが曖昧でありfalse positive/negativeのリスクが高く、案3はBL-108〜110（広範な機械的強制のコスト超過による撤回）と同型のコストリスクが高いため、まずは案1単独で様子を見る。効果不十分と分かれば案2を追加検討する。

**配置場所の判断**: BL-291本文は「call_expertのプロンプトに明記する」ことを想定しているが、実際に調査した結果、web_searchはExpert以外（task_planner/Detector/User AI等、`WEB_SEARCH_TOOL`が配線されている全ノード）からも呼ばれる共有ツールであり、同じ「事前知識由来のブランド名混入」バイアスはどのノードでも起こり得る。AGENTS.md §15.1（単一ソース・重複禁止）に従い、`WEB_SEARCH_TOOL`のtool definition（`cela_main.py:1038-1076`）という**単一の共有箇所**に指示を追加し、call_expert等の個別プロンプトへの重複記載は行わない。

追加文言（`description`内、既存のBL-188アンチパターン警告の直後あたりに挿入。**分野を限定しない一般化した文言**——固有の施設・業者名に限らず、製品・技術・規格・法令・人物・組織等、あらゆる種類の固有名詞に適用される）：
> `[BL-291] 対象カテゴリの最初のクエリに固有名詞（施設・業者・製品・技術・規格・人物・組織等、名前を持つ具体的な対象）を含める前に立ち止まってください。その固有名詞が、ゴール文・これまでのcitations・登録済みentityのいずれにも一切登場しておらず、あなた自身の記憶（事前知識）から連想しただけの場合、それはまだ検証されていない仮説です。ゴール文やacceptance_criteriaがそのカテゴリの複数性・選択肢の存在（「複数」「各種」「いずれか」等）を示唆している場合は特に、そのカテゴリの最初のクエリは中立的・網羅的な語のみとし、固有名詞を含む絞り込みクエリはその後の候補比較段階で使ってください。`

既存のBL-188「AVOID this anti-pattern」ブロックと同じ「〜しないでください」形式・同じ挿入密度（1段落）に揃える。JSON schema（`parameters`）の変更は不要。

### BL-292: task_planner〜User AI〜Expert〜Detector（独立フィールド）〜Reviewerまで6箇所、一般化した「定量的十分性」の一貫要求

用語を統一する：以下「規模適合性チェック」と呼ぶのは、「何らかの供給量・拠点数・容量・人員・予算等のリソースが、対象規模（人口・需要量・処理件数・負荷・時間等、分野を問わない）に対して量的に十分か」を、定性的な存在確認（「複数ある」「一定数確保した」等）で済ませず、定量的な比率・カバレッジ計算で判断させることを指す。商業施設や輸送力はこの一般原則の一具体例に過ぎない。

**① `call_expert`の「F-2.6 機械的検算ゲート」直後（`cela_main.py:11146-11149`）**: 既存の「数値的根拠を提示する際はpython_replで計算を実行」指示の直後に、規模適合性を扱う場合の定量計算を明記する一文を追加する。

> `[BL-292] 何らかのリソース（拠点数・容量・人員・予算等）が対象規模（人口・需要量・処理件数・負荷等）に対し十分かを論じる場合、「複数ある」「一定数確保した」といった定性的な事実だけでなく、対象規模に対する定量的なカバレッジ・比率をpython_replで計算し、成果物に明記してください。`

**②（改訂・独立フィールド化）`call_detector`のdomain_prompt、BL-278ブロック直後（`cela_main.py:12170`の直後）**: BL-266の`essence_sufficiency_concern`/`essence_sufficiency_reason`と全く同じコードパターンで、新規の独立したJSONフィールド `quantitative_sufficiency_concern`（bool）/ `quantitative_sufficiency_reason`（str）を追加する。一文をconstraint_issueの判断材料として埋め込むだけでなく、明示的に別項目として回答を強制することで、軽量・高速モデルが読み飛ばすリスクを構造的に下げる（ユーザー指摘②③）。

> プロンプト追加文言: `[BL-292: 規模適合性チェック] 上記の選定妥当性チェックとは別に、今回のタスクが「何らかのリソース（拠点数・容量・人員・予算等）が対象規模（人口・需要量・処理件数・負荷等）に対して十分か」という規模適合性の主張を含むか確認してください。含む場合、その十分性が定量的なカバレッジ・比率計算（python_repl等）で裏付けられているか、それとも「複数ある」等の定性的な事実の提示に留まっているかを判定し、後者の場合のみ'quantitative_sufficiency_concern'をtrueにしてください。'quantitative_sufficiency_reason'には、どの主張が・どの規模指標に対して未検証かを具体的に書いてください（falseの場合は空文字）。規模適合性の主張自体が今回のタスクに存在しない場合はfalseのままにしてください。`
>
> JSON schema追加: `"quantitative_sufficiency_concern": true/false, "quantitative_sufficiency_reason": "..."`

コード側の実装（BL-266のdomain_essence_concern実装パターンを完全踏襲、`cela_main.py:12207-12237`付近）:
- パース成功時: `_quant_val = domain_parsed.get("quantitative_sufficiency_concern", False)` → 文字列"true"/"false"とJSON bool両対応の正規化（既存の`domain_essence_concern`正規化コードと同型）。
- パース失敗時（JSON解析失敗によるフェイルクローズ、`cela_main.py:12211-12221`）: `domain_quant_concern = False`（BL-266同様、無関係な解析失敗で構造的な懸念まで自動的にtrueにしない）。
- fallback dict（`cela_main.py:12203-12204`の`_query_and_parse_with_retry`呼び出し）にも `"quantitative_sufficiency_concern": False, "quantitative_sufficiency_reason": ""` を追加。
- **[ユーザー指摘②を反映した機械的補強]** `quantitative_sufficiency_concern=True`の場合、`domain_constraint_issue`が`"none"`のままなら機械的に`"minor"`へ引き上げる（LLMが独立フィールドをtrueにしたにもかかわらずconstraint_issue側に反映し忘れるケースへのフェイルセーフ、AGENTS.md §15.3「機械的検証を自己申告より優先」）。BL-266のessence_sufficiency_concernは意図的にconstraint_issueと独立（別の下流＝計画再構成へ流れるため）だが、本フィールドは「今回の成果物の検証不足」という性質上、constraint_issueと連動させるのが妥当（BL-278と同じ扱い）。

**③ 数値監査パス（2段目）への転送と独立検算**: `domain_findings_block`（`cela_main.py:12241-12247`）に、②のquantitative_sufficiency_concern=Trueだった場合の指示を追加転送する（essence_sufficiency_concernは第2段に転送されず素通しのみだったが、本フィールドは第2段での**実際の検算**が主目的のため、明示的に転送する点が異なる）。

> 追加文言: `quantitative_sufficiency_concern=Trueの場合：「ドメイン妥当性レビューが規模適合性の未検証を指摘しています（理由: {domain_quant_reason}）。該当する定量計算をpython_replで独立に実行し、Agentの算出値と一致するか確認してください」`

新しいJSONフィールドは第2段には追加しない（第2段の判定は既存の`constraint_issue`へ反映、BL-266の「第2段にはこのチェック自体が存在しない」設計方針を踏襲——検算の実行は求めるが、判定の集約先は増やさない）。関数の最終return dict（`cela_main.py:12505-12511`、essence_sufficiency_concernと同じ並び）にも`quantitative_sufficiency_concern`/`_reason`を素通しで追加する。

**④（上流）`call_task_planner`の指示文品質ガイド、既存④「定性的な言及を具体的な事物・数値へ深堀りする」ブロック（`cela_main.py:10518-10530`）の直後に⑥として追加**:

> `⑥【BL-292: 規模適合性は定量的カバレッジで判断させる】何らかのリソース（拠点数・容量・人員・予算等）の充足性・十分性が論点になるタスクでは、「複数ある」「一定数確保した」といった定性的な存在確認だけをacceptance_criteriaの完了条件にせず、対象規模（人口・需要量・処理件数・負荷等）に対する定量的なカバレッジ・比率計算を指示文またはacceptance_criteriaで明示的に要求してください。`

**⑤（上流）`_USER_AI_ROLE_MANDATE`（`cela_main.py:10547-10555`）への追記**: Stage1/3（レビュー）とStage4（指示）に共通の単一箇所（§15.1）。

> `[BL-292] 特にリソース（拠点数・容量・人員・予算等）の規模適合性が論点の場合、「複数ある」「一定数確保した」といった定性的な事実だけで実質的に満たされていると判断せず、対象規模に対する定量的なカバレッジ・比率が示されているかを確認してください。`

**⑥（新規・ユーザー指摘②を反映）`call_reviewer`（最終QA、`cela_main.py:13429`）への追加チェック項目**: Reviewerは全ノード中で最終成果物「全体」を一度だけ審査する最後の砦であり、per-task単位のDetectorチェックをすり抜けた規模適合性の未検証がここで最終捕捉される。既存の「🚨 数値目標の再検証チェック」ブロック（`cela_main.py:13490-13496`）と同じ「🚨」見出し・同じ密度の新規ブロックとして追加する（Reviewerの出力スキーマは`passed`/`feedback`/`reasoning`のみで per-concern の bool 群を持たない設計のため、Detectorとは異なり新規JSONフィールドは追加せず、既存スキーマ内で表現する）。

## 検討したが見送った代替案

- BL-291の指示をcall_expertのシステムプロンプトへ直接書く案: web_search呼び出し元はExpert以外にも複数存在し、単一ソース（WEB_SEARCH_TOOLの共有definition）に置く方がAGENTS.md §15.1に合致するため見送った。
- BL-291の機械的補完案（ゴール文の複数性キーワード×entity件数1件での自動フラグ）: カテゴリの対応付けが曖昧でfalse positive/negativeのリスクが高く、BL-291自身も「該当なしとしてconstraint_issueの根拠にしない」既存BL-278の慎重な設計と同水準の精度を機械的に再現するのが難しいと判断し、まずは軽量な案1のみで様子を見ることとした。効果不十分ならBL-291を再オープンして追加検討する。
- BL-291のDetector独立探索義務化（重量案）: BL-108〜110（広範な機械的強制がコスト超過で撤回された前例）と同型のリスクが高く、BL-291自身も「非推奨」としているため見送った。
- BL-292の上流対応を、task_planner/User AIそれぞれの個別Stage（例：Stage1レビューとStage4指示を別々の文言で）に分けて書く案: `_USER_AI_ROLE_MANDATE`が既にStage横断の単一共有ブロックとして存在するため、そちらへ一本化する方がAGENTS.md §15.1（単一ソース）に合致し、見送った。
- BL-292の数値監査パス（2段目）にも独立JSONフィールドを追加する案: BL-266が「第2段にはこのチェック自体が存在しない」という設計方針を既に確立しており、第2段の役割は「1段目が拾った懸念の検算」であって新たな判定軸の追加ではないため、フィールド追加は1段目（Domain Review）のみに留め、2段目へは`domain_findings_block`経由でのプロンプト転送のみ行うこととした。
- Reviewer（最終QA）にもDetectorと同型の独立boolフィールドを追加する案: Reviewerの出力スキーマ（`passed`/`feedback`/`reasoning`）は元々per-concernのbool群を持たない設計であり、他の既存チェック項目（数値目標の再検証チェック等）もすべて同じ`passed`/`feedback`へ集約する形式のため、そこだけ構造を変えると一貫性を欠く。既存スキーマ内の新規チェック項目として追加するに留めた。
- ~~新規JSONフィールドは一切追加しない案（当初案）~~: ユーザー指摘（キャッシュ経済性の変化・軽量モデルへの構造的補強の必要性）により撤回。Domain Reviewの1箇所（quantitative_sufficiency_concern）のみ、BL-266と同型のフィールドを新設する。
