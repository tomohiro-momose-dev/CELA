## 1. なぜこの文書を作ったか

BL-224（判断の系譜の実体化）の設計中に要件定義書を精読した結果、**「何が実装済みで何が未実装か」の
一覧自体が信用できない状態**にあることが判明した。

具体的な害として、AI（Claude）が`agreements.depends_on`を「たまたま未使用の列」と誤判断し、
BL-224の初版設計で「コメントを付けて放置」と書いた。実際には要件定義§4.2がこの列を
**「依存する親Agreement IDのJSON配列 (DAG系譜)」**——判断の系譜そのもの——と定義していた。
**誤認は既に実際の設計ミスを生んでいる。**

## 2. 検証方法

- **全判定に`file:line`の証拠を付ける。** 証拠のない判定は書かない（AGENTS.md §14）。
  「未実装」の場合は使用した検索語を明記し、不在を後から検証可能にする。
- **要件定義書の付録B.1は参照しない。** 陳腐化しているため、実コードのみを根拠とする。
- **関数名の一致で判定しない。** 本文を実読する。名前が要件に一致していても中身が別物である
  ケース（下記⚠️）が実在するため。
- 一次調査はExplore agent 3体を並列で使用。**判定が意外なもの（⚠️・🗑️）は報告をそのまま採用せず、
  Claudeが自分で実コードを開いて再確認した**（AGENTS.md §16.2: レビュー所見は入力であり指示ではない）。

### 判定語彙

| 記号 | 意味 |
|---|---|
| ✅ | 実装済み。要件の意図を満たしている |
| 🟡 | 部分実装。**何が欠けているかを明記する** |
| ❌ | 未実装。該当コードなし（検索語を明記） |
| ⚠️ | **名前だけ実装**。関数・テーブルは存在するが中身が要件を満たしていない。読む人が「実装済み」と誤認するため最も危険 |
| 🗑️ | **死蔵**。実装され書き込まれてもいるが、誰も読まない・消費しない（AGENTS.md §15.4） |

⚠️と🗑️は本調査で必要性が判明した新カテゴリであり、**この2つを可視化することが本文書の主目的**である。
従来の3値（✅/🟡/❌）では「あるように見えるが機能していない」を表現できず、それがまさに
今回の誤認を生んだ。

## 5. 構造的所見

個別要件に紐づかない、横断的な設計の歪み。

### 5.1 会話履歴は「設計された場所」に永続化されていない

要件§4.5は`chat_history`テーブルを定義し、F-6は「SQLite 3 **完全**永続化」を謳う。実際には:

- `chat_history`テーブルへのDB操作は**0件**（作られるだけの空テーブル）
- 会話履歴はLangGraphの`SqliteSaver`が**別のDB**（`CELA_CHECKPOINT_DB_PATH`、`cela_main.py:13950-13952`）へ
  state全体のブロブとして永続化している

つまり会話は失われてはいないが、**`cela.db`からトピックや時刻で問い合わせられる形にはなっていない**。
この帰結として:

- **F-8.4(1)の時間減衰検索は構造的に実装不能**——検索対象の`chat_history`が問い合わせ可能な形で
  存在しないため。要件を実装しようとした時点で初めてこの障壁に気付くことになる。
- BL-222の`_audit_report`（人間監査ビュー）も会話文脈を表示できない。

### 5.2 「後続へ申し送る」という単一の概念に9つの別実装

| 系統 | 実装 |
|---|---|
| issue_log系（6） | `_build_escalation_pin_text` `3992` / `_build_deferred_issue_pin_text` `4015` / `_build_open_issue_pin_text` `4070` / `_build_escalation_resume_notice` `4116` / `_get_forced_escalated_issues_text` `6389` / `_build_human_input_answered_notice` `6788` |
| plan_drafts系（3） | `_append_deferred_note_to_plan` `6081` / `_get_deferred_notes_text` `6164` / `_get_reviewer_comments_text` `6189` |

それぞれ別テーブル・別条件・別表示形式を持ち、**各々を`call_expert`/`call_detector`/
`generate_user_utterance`の3ノードへ個別に配線する**必要がある。結果として同型の配線漏れが
繰り返し発生している——BL-082（Userブランチだけ配線漏れ）、BL-219（承認時に届かない）、
BL-223（橋渡しが発火しない）。AGENTS.md §15.2「部分的な保護は無いよりも危険」の構造そのもの。

### 5.3 プロンプト末尾の無制限な肥大

`system_prompt_trailing +=` は`call_expert`内だけで**16回**、ファイル全体で**30回**。
1つのBLが1ブロックを足す構造で、追加は容易だが全体像を誰も把握できない。BL-220が
BL-185の不変条件（差し戻し通知がtrailingの最後）を壊しかけたのは、この構造の必然的な帰結。

### 5.5 「名前は要件どおり、中身は別物」が3箇所ある（本調査の最重要発見）

読む人（AIも人間も）が「実装済み」と誤認する状態。今回、実際にこの誤認が設計ミスを生んだ。

| 箇所 | 名前が示すもの | 実際の中身 |
|---|---|---|
| `_build_hydrate_context`（`7436-7449`） | F-8.2「Hydrate Refresh 5節」 | `decisions`直近N件を箇条書きにするだけ。5節構造ゼロ。F-8.1の非対称圧縮も無し |

加えて**コメント自体の陳腐化**も確認された: `2395-2397`はFreezeツールを「D-045で一時休止、tools配線を外した」と

### 5.6 要件が想定したモデル二層化が実現していない

F-5.2・F-10.1・F-7.4はいずれも「思考モデル（監査）と即答モデル（実行）の物理的な使い分け」を
求めているが、`model_*`変数18個のうち**14個が同一の`hy3`**（`313-349`、Claude再確認済み）。
差別化はtemperature（`4792`）とreasoning_effort（`4866-4876`）のみ。
ノード別変数という「器」は用意されているため、**設定値を変えるだけで要件に近づける**——
実装コストが最も低い乖離のひとつ。

### 5.7 意図的な不実装が要件定義書へ反映されていない

- **F-7.3（ロールバック）**: `6448`で「[BL-075/D-047] rollback_whiteboard（F-7.3）は撤廃した」と
  明記され、現行方針は「最新版を保持したままeditsで部分修正」。設計判断として妥当だが、
  **要件定義書F-7.3は今もロールバックを要求したまま**。
- **F-9.1（sqlite-vec/embedding RAG）**: `6955`のコメントで「embeddingベースのRAGは今回導入しない」と
  意図的に不採用。しかし要件定義書F-9.1はsqlite-vecを要求したまま。

要件を実装しないと決めたなら、要件側にその判断を書き戻さないと、次に読む人が
「未実装＝やり残し」と誤解して不要な作業を始める。
