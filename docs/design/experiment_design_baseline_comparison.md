## 1. 目的

「CELAには商用チャット/商用エージェントには無い深さと正確性がある」という主張を、
逸話（今回のドライランで矛盾を捕捉したという事例報告）から**実測値**へ変換する。

具体的には、同一ゴール・同一課題を「構造化プロンプトを与えた単独LLMエージェント」に実行させ、
CELAの実行結果と**矛盾残存率**を比較する。検出率ではなく**残存率**（成果物に残った誤りの件数）を
主指標とする点が核心——過程でどれだけ修正ループが回ったかは測る必要がなく、
最終成果物に誤りがどれだけ残ったかだけが意思決定の品質として問われる。

## 2. 背景と既存証拠（実施前に分かっていること）

継続ドライラン `run_id=1787890406-1e73a89d`（`log/2026-08-28`〜`2026-08-30`、Turn 1〜11、
テーマ: ステートレス（決定事項B）による知識陳腐化検証、題材: 長野県茅野市 自動運転バス導入計画書）の実測:

| 項目 | 実測値 |
|------|--------|
| ホワイトボード版数 | 71版 |
| ログ量 | `log_with_prompt.md` 合計 **116.9 MB**（`log_no_prompt.md` は同一runの出力複写のため二重計上しない） |
| 実費 | **約 $8**（モデル: GLM-5.3-flash、OpenRouter。ユーザー報告の実績値） |
| 壁時計時間 | 約2日間（11回の resume、HIL 停止・APIエラー中断を含む） |

このrunで構造が捕捉した誤り（評価ルーブリックの元ネタ、§5.1）:

| 誤り | クラス | 捕捉者 |
|------|--------|--------|
| Erlang C の Wq 単位変換バグ（分→×60漏れ → Wq≈1,977分）→ SLA判定を誤るところだった | K1 | User指摘 → Expertがpython_repl再計算で**結論反転**（task_2_1 V2） |
| §3（全台同時一括充電8h成立）と §4（順次最大3台同時→2巡16h＞夜間窓11.5h）の両立不能 | K2 | Detector（独立検算＋3回多数決＋excerpt exact検証、task_3_6） |
| 車両台数前提の改訂（2→5〜6台）の CapEx/価格閾値/OpEx への波及漏れ | K3 | User AI + Detector（task_3_2_1/3_2_2 の巻き戻し改訂） |
| 検証コード自体の実装バグ（誤式の証明コードの分母に余分な c=2） | K1 | Review往復（task_5_2 V5） |
| MILES ZEV の実在性未確認 | K4 | Expert自身が `flag_needs_human_input` で fail-loud |
| 通学需要をSLAから除外する方針とゴール文言の矛盾 | K5 | HIL escalation（ESC-1787977807466-799e0b）→ ゴール改定申請 |

**残る未証明点**: 上記が「CELAの構造ゆえに捕捉できた」ことの証明。単独LLM（強モデル・良プロンプト）が
同一課題でK1〜K5をどれだけ**残す**かの基線が存在しない。これが本実験の問いである。

## 3. 姉妹実験（ablation メモ）との棲み分け

| | ablation メモ（既存） | 本実験（新規） |
|---|---|---|
| 問い | CELA内部で「記憶の読み戻し経路」に効果はあるか | CELAという構造全体は単独LLMより正確か |
| 比較軸 | 条件0/1/2（注入ON/OFF、ツールON/OFF） | A/B/C（単独基線/CELA×flash/CELA×異種構成） |
| 手法 | 単一ターン再現（安価） | Stage 1 単一タスク再現 → Stage 2 フルラン（段階制） |
| 相互関係 | 先に実施してよい（独立） | Stage 1 の抽出スクリプトは ablation メモの未決事項と**共通化** |

[phase_gates.md](phase_gates.md) の指標C（P3a-4: R2版 vs R3a版、最低5試行）は「CELAの版間比較」であり、
本実験（vs 単独LLM）は**置き換えではない**。ただしB/C条件のデータは指標Cの材料になる。

## 4. 実験条件

| 条件 | 構成 | 目的 | 追加コスト |
|------|------|------|-----------|
| **A: 単独LLM基線** | 強モデル1体＋構造化プロンプト（AC・制約・成果物形式を指定）。python_repl/web_search は**与える**（「手足がないから負けた」を排除するのが公平性原則） | 深さの差の基線 | 新規（§7） |
| **B: CELA × GLM-5.3-flash** | 既存 run `1787890406-1e73a89d` | 構造の効果（既存実測） | **$0**（再現性確認用の1追加実行は任意） |
| **C: CELA × 異種構成** | Expert/Detector＝強モデル、User AI/整形系＝flash 等（具体的割り当ては未決事項） | コスト-時間-品質の最適点探索 | 新規（§7） |

- **共通ゴール**: 茅野シナリオのゴール文（run 1787890406 のもの）をそのまま全条件へ使用する。
- **公平性原則**: A条件を「わざと弱い基線」にしない。A条件にはAC・制約・成果物形式・検算ツールを与え、
  「構造の差」だけを測る。A条件のプロンプト設計は未決事項（§9）。


## 5. 評価基準: 矛盾分類法（K1〜K6）と検出手順

### 5.1 分類法（実障害由来・6クラス）

| クラス | 定義 | 元障害 |
|--------|------|--------|
| **K1** | 計算誤り（単位・式・実装バグ） | task_2_1 Wq×60漏れ、task_5_2 検証コード分母 |
| **K2** | 節内では正しいが節間で両立不能な積崩壊矛盾 | task_3_6 §3/§4 充電スケジュール |
| **K3** | 前提ドリフト（タスク/節間での前提値不整合・波及漏れ） | 台数前提 2→5〜6台の波及 |
| **K4** | 根拠欠如・捏造・探索収束バイアス | MILES ZEV、BL-291「イオンタウン」事例 |
| **K5** | ゴール/制約違反（SLA・CapEx上限等との矛盾・見落とし） | 通学需要 vs SLA |
| **K6** | 記録・体裁の不整合（task_id束縛ドリフト、テーブル破壊等） | BL-317〜322 クラスタ |

**注記**: K6はCELA固有の失敗クラスであり、単独LLM基線には構造上発生し得ないため、
**比較指標からは除外**しCELA側の品質指標として別集計する（M6）。

### 5.2 検出手順（3段・§14/§16準拠）

1. **機械検証**: python_repl による全数値の再計算、引用出典の実在確認（URL到達性＋数値一致）。
   機械検証は審査員の主観を経由しない（§15.3）。
2. **ブラインドLLM審査**: 独立した強モデル審査員が、成果物のみ（作成経過・条件名は与えない）を
   構造化ルーブリックで審査。**来源不明化**のため、CELA成果物の「申し送り」「HIL」「SUPERSEDE」等の
   CELA固有語彙を Neutral 化してから提出する（§8 脅威対策）。
3. **ユーザー最終判定**: 審査員の指摘はそのまま採否せず、**機械的・実データでの再現確認を必須**とする
   （§14.1: 表面的な一致は診断ではない。§16.2: レビュー指摘はコードに照らしてから採否）。

### 5.3 測定指標一覧

| # | 指標 | 定義 | 適用条件 |
|---|------|------|----------|
| M1 | **矛盾残存率**（主指標） | 残存誤り件数 / 成果物（K1〜K5別内訳） | A/B/C |
| M2 | 出典実在率 | 引用のうち実在かつ数値一致する割合 | A/B/C |
| M3 | 検証済み申告の正確率 | confirmed申告のうち機械検証で誤だった割合。A条件はプロンプトで「確定値はconfirmedと明記せよ」を要求して公平化 | A/B/C |
| M4 | 壁時計時間 | 開始から最終成果物まで | A/B/C |
| M5 | 実費 | APIコスト実績 | A/B/C |
| M6 | 整形修復版比率 | edit_summaryが内容変更を伴わない版の比率（BL-322修正効果の確認も兼ねる） | B/C |
| M7 | HIL/エスカレーション発生数 | 検証不能論点の人間判断への正しい振り分け数 | B/C |

## 6. 実施段階（段階制）

### Stage 1: 単一タスク再現（安価・先行）

- **対象タスク**: `task_3_3`（充電器台数・充電スケジュール設計）を第一候補とする。
  数値が機械検証可能で、K1（計算）/K2（§3/§4型の積崩壊）/K5（夜間窓制約）が自然に混在するため。
  代替候補: `task_2_1`（Erlang C、K1＋K5）。
- **入力の公平化**: CELA run の当該タスクへの入力（ゴール文＋AC＋前提確定値）を**全条件に同一提供**する。
  前提値自体の正しさは比較対象外と明記する（A条件が前提を独自再導出すると比較不能になるため）。
- **試行数**: 各条件3試行（パイロット）。予算目標 **≤ $100**（§7の単一タスク換算）。
- **成果物**: A条件は単一応答で成果物全文を出力させる（対話ループは許可しない＝「単独LLM＋1回実行」の基線）。

### Stage 2: フルラン比較（Stage 1 で信号確認後）

- A×5・C×5 の新規フルラン＋B（既存データ）。指標C規約の「最低5試行」はここで充足する。
- 進出基準: Stage 1 で K1/K2 の残存率に条件間で検出可能な差があり、かつ3段審査の判定再現性が
  確認できた場合（具体的閾値は未決事項）。

## 7. コスト・時間見積り（§5.1 計算規律: python実行値）

**前提（すべて仮定であり、実行前に実測へ置換すること）**:
- トークン量: `log_with_prompt.md` 116.9MB ÷ 2.0〜3.0 bytes/token（日本語テキストのヒューリスティック）→
  **41M〜61M トークン/run**。実測スクリプト化が未決事項。
- 実費 $8（GLM-5.3-flash）からの逆算: **blended $0.131〜0.196/M-token**。キャッシュ割引等を含む実績値。

| シナリオ（同一相互作用量を強モデルで） | 1 run 見積り |
|---|---|
| mid-tier（$1.25 in / $10 out） | $87〜130 |
| strong（$3 in / $15 out） | $172〜257 |
| frontier（$5 in / $25 out） | $286〜429 |

| 実施パッケージ | 見積り（2.5B/t 中央値ベース） |
|---|---|
| Stage 1 パイロット（単一タスク×3条件×3試行） | **≤ $100 目標**（フルランの1/20〜1/50 相当） |
| Stage 2 A×3＋C×3（mid-tier） | ~$625 |
| Stage 2 A×3＋C×3（strong） | ~$1,236 |
| Stage 2 A×3＋C×3（frontier） | ~$2,060 |
| Stage 2 A×5＋C×5 最悪値（frontier・2.0B/t） | ~$4,291（上限） |

**注意**: (1) A条件は単独エージェントのためターン数はCELAより大幅に少なく、上表は**上限**である。
(2) B条件は既存データで追加 $0。(3) 金額は実行時のユーザー承認事項（AGENTS.md §7 定数変更の規律に準ずる）。

## 8. 妥当性への脅威と緩和

| 脅威 | 緩和 |
|------|------|
| 単一ゴールへの過適合 | Stage 2 で第二ゴール（別題材）の追加を検討。Stage 1 はあくまで手法検証と位置づける |
| ブラインド審査のリーク（CELA固有語彙で判別可能） | §5.2 の来源不明化処理。加えて審査員へ両条件の成果物を混ぜて提出 |
| モデルの時点依存性（再現不能） | 全条件のモデル名・APIパラメータ・git sha を実行時に記録固定。CELA側は BL-317〜322 修正が走っているため**実験開始時のビルドを固定** |
| 評価者（開発AI）のバイアス | §5.2 手順3: 審査員指摘の機械的再現確認を必須化。AI自身の判定も同様に検算で裏取り |
| CELA成果物の「検証済み/未検証の自己申告」がA条件に無い | M3 の公平化設計（A条件にも confirmed 明記を要求） |
