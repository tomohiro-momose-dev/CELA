# 8フェーズ・22タスク・225件の合意を、無人で破綻なく積み上げられるか——「安いモデル×アーキテクチャ」の実測

## はじめに

CELAは、LangGraphで組んだマルチエージェントの合意形成システムです。個人開発で、あえて数字的に無理のある制約（過疎地域への自動運転バス導入計画、公的補助CapEx上限1億円・年間市費OpEx上限4,000万円・待ち時間SLA20/30分、路線バス廃止済み、という現実的だが厳しい前提）をゴールとして与え、AIたちがどう格闘するかを観察しながら、監査・ガバナンスの仕組みを育てています。

今回は、2026年8月11日の1回のドライラン（run_id=`1786337594-17df8ff3`、GPT-5.6 luna・$0.6/1Mトークンという廉価モデルを使用）が、8フェーズ・22タスク・225件のDeliverable agreementsを、人手介入ゼロで最後まで積み上げた結果を、後から**独立に検証した記録**です。「無介入で動いた」という報告だけでは何も証明したことにならないので、実際に成果物の中身を読み、財務計算を自分でも再計算し、facilitatorという停滞救済機構の呼び出し履歴まで1件ずつ追いました。

## 1. 財務計算を独立に再計算したら、全部合っていた

`task_5_1`（CapEx比較4案）と`task_5_2`（年間OpEx・運賃収入3シナリオ）の数値を、成果物のテキストから式を抜き出してPythonで独立に再計算しました。

CapEx（一括購入案A）：`4台×20百万円＋設備等28百万円＝108百万円`、予備費5%を乗せて`113.40百万円`。段階導入案C・既存設備活用案Dも含め、4案すべて成果物記載の数値と完全一致。

OpEx（O1案）：人件費12.0＋電話予約6.0＋遠隔監視18.0＋電力1.5＋保守6.0＋保険1.2＋通信1.2＋停留所維持1.0＋冬季対応2.5＝`49.4百万円`。O2=74.1、O3=109.0も含め一致。運賃収入も基準ケース`100,000件×300円＋30,000件×150円＋配賦3.0−返金0.2−未収0.3＝37.0百万円`で一致。

面白いのは、この正確さの理由が「モデルが賢いから」ではなさそうだという点です。成果物自身に「Pythonで検算した」という一文があり、実際にログにも同様の自己検算の痕跡が残っています。CELAには「python_replを一度も使わずに数値主張をしたら差し戻す」という機械的なfail-closedゲートがあり、モデルの暗算力に頼らせない設計になっています。安いモデルでも計算精度が保たれた理由は、モデルの知能というより、**モデルに計算をさせない構造**にあると考えています。

## 2. 8フェーズを貫通して、制約が1文字も劣化しなかった

最初のゴール文にある絶対制約——CapEx「1億円以内」、OpEx「年間4,000万円以内（1円でも超えたら議会否決）」、SLA「市街地20分以内・山間部30分以内」——は、8フェーズ・数十ターンを経た最終ゲート判定（`task_8_2`）でも「100百万円」「40百万円」「20分／30分」として一字一句そのまま引用され続けていました。長時間の多段タスクにありがちな「途中で前提が薄まる」「後半のタスクが忘れる」という劣化は起きていません。

これは、会話履歴に頼る記憶ではなく、`agreements`/`whiteboard_drafts`という構造化DBから毎ターン文脈を再構成する設計（各ノード呼び出し自体はステートレス）によるものだと考えています。モデルの長文脈維持能力を試すのではなく、記憶を都度組み立て直す構造そのものに劣化耐性を持たせる、というアプローチです。

## 3. 「54版まで肥大化した」は暴走ではなく、抜け穴を塞ぐサイクルだった

最終タスク`task_8_3`（最終計画書）は50版まで改訂を重ねました。版数だけ見ると暴走しているように見えますが、実際の改訂内容を1件ずつ追うと、様相が違います。

```
v9   ハード制約の待ち時間起点（t0〜t5）の記述矛盾を是正
v13  5つの分岐条件を、担当主体・必要証憑・判定単位まで一対一で対応付け
v29  運賃収入の二重計上・除外漏れの防止ルールを追加
v30  「目安」という曖昧表現を削除し、必須合否条件へ格上げ（ユーザー差戻し指示）
v31,33-34  「議会承認があれば上限超過を実施できる」と誤読され得る抜け穴を明示的に封鎖
v44-49     即時配車と事前時刻指定予約でSLA起点の定義が違う、という後発の精度課題を修正
```

さらに、DetectorとExpertが交互に版を作る規則的なパターンがあります。Detectorが監査注釈を挿入し（偶数版）、Expertがその指摘を本文へ統合して注釈だけを削除する（奇数版）、という往復です。単調に増えているのは文字数ではなく、**見つかった抜け穴の数**でした。これはコンテキスト崩壊やハルシネーションの蓄積というより、批判と統合の反復によって仕様が収束していくプロセスに見えます。

## 4. 最終判断は「本運行不承認」——安易な承認をしなかった

`task_8_2`の最終ハード制約ゲート判定は、CapEx・赤字補填・市費総負担・市街地SLA・山間部SLA・安全・アクセシビリティ・電話予約・労務・冬季の全ゲートを「判定不能」または「本運行移行不可」としました。判定文にはこう明記されています。

> これは未確認事項を違反なしと扱う判定ではない。実績・証憑がない項目は判定不能、開始停止条件に関わる未確認事項は本運行移行不可として扱う。

さらに、財務では独自に算出した運賃収入34.5百万円と、別タスクで試算した37.0百万円の差異2.5百万円を**自分で検出**し、解消するまで確定させない、という監査的な態度を貫いています。「無理な制約をどう格闘して解くか」ではなく「解けないことを誠実に証明できるか」という、このプロジェクトが最初から狙っていたストレステストの、1つの成功例だと考えています。

## 5. 一番の発見：停滞救済機構（facilitator）の呼び出し予算の半分は、議論の深さ不足ではなくバグの繰り返し通知に消えていた

CELAには、Expert-User間の議論が停滞したときに、別視座からの示唆を挟むfacilitatorという役割があり、run全体で累計6回まで、という予算制限があります（超えると強制停止）。この6回を1件ずつ内容まで読んだところ、意外な内訳でした。

**前半3回（phase_3付近）**は、すべて同一症状の繰り返し診断でした。

> 「現在の停滞は、電話予約設計の内容そのものではなく、正式なタスク切替後も実行コンテキストが`task_3_2`に固定されているという、実行状態と指示の不整合に起因しています」

ユーザーが次タスクへの切替を3ラウンドにわたり明示的に指示しても、Expert側は毎回「システム上の現在タスクは依然として`task_3_2`のままでした」と返すだけで、機械的なタスク遷移自体が成立していませんでした。facilitatorは3回とも正確に原因を言い当てていますが、**指摘が生きて反映された形跡がなく、同じ診断が繰り返し消費されるだけ**でした。

**後半3回（phase_8付近）**は対照的に、いずれも具体的な提案がその後の成果物改訂に実際に反映されています。「判定不能ゲートの解消条件に議論を集中させよ」「本運行判断とゲート未確認を切り分けよ」「反復される状態記録から条件分岐付きの承認案へ変換せよ」——3回とも、次の版で構造として実装されていました。

つまり、**「facilitatorの上限を上げれば議論がもっと深まったか」という問いへの答えは、単純ではありません。** 後半だけを見れば明らかに中途半端に打ち切られています。しかし上限を上げるだけの対応は誤りで、前半の浪費パターンは予算をいくら増やしても再発します。「議論が足りない」のではなく「機構側のバグが議論の予算を先食いしていた」というのが実態でした。この種の限界は、facilitatorをいくら賢いモデルに載せ替えても解決しません。遷移機構自体の正しさが前提になっているからです。

## 6. 「安いモデル＋アーキテクチャ」で何が代替でき、何が代替できないか

これらの観察をまとめると、次のような整理になりました。

**代替できている（今回の実測で裏付けあり）**：計算精度（fail-closedゲートがモデルに暗算をさせない）、複数ロールの独立レビューによる誤り捕捉、構造化DBによる長期の文脈保持。

**代替できていない**：前提そのものを疑う判断の深さ（facilitatorは示唆を与えられても、モデル自身が前提を投げ捨てる決断をするかは別問題）、そして**機構自体が壊れているときの耐性**（facilitatorの正しい診断が3回続いても、機構側のバグは直らなかった）。

もう1つ、コスト面で見落としがちな点があります。安いモデルでの成功は「無料」ではなく、「多くのターン数」というコストで買っています。54版に達した最終タスクは、強いモデルなら少ない反復で済むところを、多段検証の反復で埋め合わせている可能性が高く、トークン単価が安くても、タスクあたりの総消費トークンはむしろ増えているはずです。「安いモデル＋アーキテクチャ」対「高いモデル単体」の総コスト比較は、まだ検証していません。

## なぜこれを書いているか

「AIエージェントに任せたら中身がどうなっているか分からない」「結局人間が全部見返す羽目になる」というボットシッター疲れの声を、最近よく見かけます。このプロジェクトは個人のドライランに過ぎず、実運用の実績もありません。ただ、無介入で走らせた成果物を後から独立に検証する、というプロセス自体は、企業がAIエージェントを導入する際にも同じように必要になるはずです。今回のような「良かった点（計算精度・制約保持）」と「悪かった点（機構バグによる予算浪費）」を両方隠さず書くことが、同じ課題に取り組む誰かの参考になればと思い、書き残しておきます。
