# Long-Term Agent Hydrate Hypothesis

## Origin

本研究の出発点はソフトウェア開発ではない。

元々は Gemini や ChatGPT 等の長大なチャットにおいて、

* コンテキスト破壊
* ハルシネーション
* スレッド移行
* AIとの関係性の再構築

に大きな認知コストを感じたことにある。

新しいチャットを開始すると、

* 過去の議論
* 問題意識
* 思考の流れ
* 会話の調子

が失われる。

技術的な要約だけでは不十分であり、

「仕上がった相棒としての状態」

を維持できないことが本質的な課題だった。

---

# Hydrate Concept

Hydrate とは単なる要約ではない。

目的は

「AIが再び同じ状態から思考を継続できること」

である。

Hydrate が保持するもの

* 憲法
1.主目標
2.ガードレール

例：都市運営simで例えると
主目標：犯罪率0%、幸福率100%、この状態を可能な限り持続可能な都市運営

ガードレール：
・エージェントは犯罪行為を行わない
・極端な圧政や抑圧などを行わない


* state/mode
具体的には例えば今は、議論モード、タスク実行モードなど
（他にもいくつか状態で分けるべきと思う）
このモードの違いによって、DBに読みに行くべきものなど
下準備で何が必要かが変わると思われる



* 現在の目標
* 現在地
* 決定事項
* 未解決課題
* 会話の文脈
* 重要な仮説
* ユーザーの意図

例えば、議論モード

・現在の目標（何を議論する、なぜする？、前提条件）
・現在地
・決定事項（選んだ事、理由、選ばなかった事、理由、長くなりそうなのでDBへリンク）
・未解決課題（現在の議題以外の課題は過去に議論したのか、まだなのか？その時の議事録は？優先度は？）
・議論の流れ（これは直近Nターン生ログ、segment等、かなり過去の議論はdbで紐づけ)
・重要な仮説
・会話の文脈（これは議論の流れと同義？）
・ユーザーの意図（エージェント同士なら、エージェントが推進する意見等かな？）
・正式決定ではないが議論の中で出てきた”小さな”合意、前提の共有事項

・議論の中で前提条件が変化すれば、その前提条件で適合できそうな過去に無効化された議論も探索する

例えば、タスク実行モード

・現在の目標（何を実行する、なぜする？、前提行健）
・現在地（プランがあるなら、フェーズやタスクの位置）
・決定事項（タスク達成のために自己的に選んだ事、理由、選ばなかった事、理由、長くなりそうなのでDBへリンク）
・未解決課題（タスク実行中に出てきた壁、制約、優先度（優先度次第ではタスク順位切替）、またはバックログ的な未実行タスク、優先度）
・議論の流れ（タスク処理なら、タスク処理のNターン生ログ、segment等、または行動、実装ログ的なもの（行動、実装ログは別DBに非圧縮の完全な形で残してリンク)
・重要な仮説(タスク実行中に得られた仮説、なぜその仮説、理由）
・会話の文脈（これは議論の流れと同義？）
・ユーザーの意図（タスク実行なら、エージェントが考えた行動プランなど？）
・タスク内で守らなければいけない規範など

Hydrate が保持しないもの

* 全会話ログ（直近Nターンは保持）
* 冗長な履歴

# Discovery

Cursor、Claude Code、Memory.md 等を調査する中で発見したこと。

現在主流の Memory 系手法は

「タスク継続」

には強い。

しかし

「長期文脈維持」

には必ずしも最適化されていない。

Memory.md は

* 次に何をするか

を引き継ぐ。

Hydrate は

* なぜそうなったか
* 今どの文脈にいるか

を引き継ぐ。

目的が異なる。

---

# Goal Drift Discovery
* 別エージェントとして実装

議論を進める中で、

本質的な問題はチャット引き継ぎではないことが判明した。

より大きな問題は

Goal Drift

である。

定義

「元の目標が失われ、
局所最適な判断が積み重なり、
最終的に本来の目的から逸脱する現象」

これは

* 人間
* AI
* プロジェクト
* 組織

全てで発生する。

---

# Hypothesis Drift
* 別エージェントとして実装

さらに重要な発見。

現実世界では

仮説

↓

暫定決定

↓

既成事実

へ変化する。

例

* 概算見積
* 暫定仕様
* 会議中の思いつき
* AIの提案

これらが十分な検証なしに

「決まったこと」

へ変化する。

この問題を

Hypothesis Drift

と呼ぶ。

---

# Assumption Drift Detector
* 別エージェントとして実装

昔の前提条件が
まだ成立していると思い込んでいないかを監視、判断


---

# AI Era Risk

AI時代ではこの問題が加速する。

理由

AIは大量の仮説を高速生成する。

その結果

仮説

↓

会話

↓

再利用

↓

前提化

↓

決定事項化

が極めて高速に発生する。

---

# Confidence Problem

単なる回答の正誤よりも

前提の確信度

が重要である。

例

「あとはいくつ？」

↓

AI

「7」

↓

実際の答え

「3」

（あと = 跡）

問題は回答ではなく、

どの解釈を採用したか

である。

必要なのは

Answer

Reason

Assumption

Confidence

を同時に保存すること。

---

# Decision Log vs Assumption Log

一般的な監査は

Decision Log

を残す。

しかし本当に重要なのは

Assumption Log

である。

記録例

* 何を仮説としたか
* 確信度
* 根拠
* 検証状態

仮説が決定事項に昇格した瞬間を追跡できる。

# Long-Term Agent Experiment

研究仮説

Hydrate は長期稼働エージェントに有効である可能性がある。

実験群

A: 通常エージェント

B: Hydrate

C: Hydrate + Goal Drift Detector

D: Hydrate + Goal Drift Detector + Decision/Assumption Log

評価項目

* Goal Retention
* Task Completion Rate
* Hallucination Recovery
* Context Reconstruction Cost
* Decision Traceability
* Idea Diversity
* Hypothesis Drift Frequency

# Current Conclusion

Hydrate の価値は

「チャットを引き継ぐこと」

ではない。

本質的価値は

* 文脈維持
* 仮説管理
* Goal Drift防止
* 意思決定監査

である。

そして将来的には

AI協働における

"Project State Hydration"

へ発展する可能性がある。

これは単なる会話要約ではなく、

プロジェクトの認知状態そのものを継承する試みである。
