## 各社の思想の違い

### Snowflake: SQL・DWH中心のコンテキスト
Snowflakeは「信頼性の高い構造化データ」と「整理されたセマンティック層（指標の定義など）」を強みとします。BIアナリストやSQL主導の組織において、間違いのないビジネスコンテキストをAIに与えることに長けています。

### Palantir: 事業運用（オントロジー）中心のコンテキスト
Palantir AIPは、単なる「データ」ではなく「事業の仕組みそのもの（オントロジー）」をコンテキスト化します。たとえば「在庫が切れたらどの工場から補填し、誰の承認が必要か」という業務のアクションとルールまでAIに理解させます。

### Microsoft: 業務現場（Office/Power BI）中心のコンテキスト
従業員が日常で使うTeams、Power BI、Excel、SharePointなどの「作業現場の文脈（Microsoft Graph）」をAIに与えることで、ユーザーが意識せずに高度なAI支援を受けられる環境を作っています。

## まとめ

Databricksは、単に「LLMを使えるプラットフォーム」ではなく、「企業内のあらゆるデータ、使用履歴、メタデータ、ガバナンスルールをAIに与え、AIを賢くするためのインテリジェンス層」としての立ち位置を確立しようとしています。

- **Databricksを選ぶべきケース**: 非構造化データ（画像・ログ・テキスト等）と構造化データが混在しており、データサイエンティストやエンジニア主導で高度なAIエージェントやカスタムRAG/複合AIシステムを構築したい場合。
- **他社を選ぶべきケース**: 厳密なSQL/BI中心ならSnowflake、現場オペレーションの自動化・オントロジー構築ならPalantir、Office環境と強力に密着させたいならMicrosoft Fabricが有力な選択肢となります。

## CELA との位置づけ（注記）

上記はいずれも「企業データ／業務」を文脈源とする本番プラットフォームであり、CELA のように
**エージェント自身の「判断とその理由」を系譜として残し、次の思考の文脈に再構成する**という
開発プロセス内（in-IDE）の系譜哲学とは層が異なる。共通するのは「文脈をどう構造化し、誰/何に
与えるか」という問いであり、CELA の relation_edges（agreement/fact/entity）や BL-228 の
chat_history スパインが目指す「調子（どう一緒に考えていたか）の再構成」は、Palantir の
オントロジー的アプローチ（意思決定ルールの系譜化）に最も近い志向を持つ。
