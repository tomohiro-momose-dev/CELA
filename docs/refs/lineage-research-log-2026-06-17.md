## Phase 0: 出発点の再確認

### 痛みの原点
チャットスレッドを切り替えると「初めまして」になり、議論の調子（tuning）が戻らない。ダッシュボードやBACKLOGだけでは「次のタスク」は引き継げても「一緒に考えていた空気」は引き継げない。

### Cursorでの実証データ
- Hydrateなし：1ターン目に約90kトークン消費、2〜3ターンのリハビリが必要
- Hydrateあり：1ターン目に約50kトークン、即戦力
- 重要な追加発見：情報の構造化（BACKLOG・実装ログ）が十分であれば、Cursor自体が優秀でファイルを自律的に発見できる。つまりHydrateの価値は「構造化された環境」では相対的に下がる

## Phase 1: 問題の再定義（戦略の二軸化）

### 当初の仮説の修正
汎用AIチャットへの「チャット引き継ぎ」需要を調査した結果、以下が判明した。
- 一般ユーザーの大多数は数ターンで会話を終える
- コンテキスト容量に課金できるヘビーユーザー（弟の事例）はチャット引き継ぎで困っていない
- 需要があるのは少数のヘビーユーザー層のみ

### 業界トレンドとの接続
「SaaS is Dead」という潮流について、弟（IT業界・AIエージェント開発・企業内製化案件）から得た知見：
- AIによる実装コストの低下で内製化・カスタムアプリへの移行が進んでいる
- コードレビューの概念が変わりつつある（AIが書き、AIが直す前提のワークフロー）
- ただし「責任の所在」は人間に残るため、判断・決定の監査需要は残る

### 実験概要
AIモデル版シムシティとも言われる長期マルチエージェント実験。
- Gemini 3 Flash：15日間で683件の犯罪を蓄積
- Grok 4.1 Fast：約4日で183件の犯罪を犯し世界崩壊

- Claude：唯一犯罪ゼロ
- 重要な知見：エージェント社会は緩やかに劣化するのではなく、臨界点で「完全協調」か「即時崩壊」のいずれかに転じる。監視して介入する方式では手遅れになりうる

### 学術的裏付け
- arXiv:2505.02709（Goal Driftの定量化）：コンテキストが長くなるほどパターンマッチング行動への依存が強まり、それがGoal Driftの主要メカニズムであることを実証。最良のエージェント（Claude 3.5 Sonnet + スキャフォールド）でも10万トークン以上で完全な目標遵守を維持できたが、全モデルで何らかのドリフトが観測された
- Decision Provenance（業界用語）：エージェントの判断の背後にある入力・推論・出力の連鎖を再構築する能力。2026年に入り戦略的コントロールプレーンとして語られ始めている
- Agent Execution Record（arXiv:2603.21692, Oracle Cloud Infrastructure）：既存ツール（LangGraph, LangSmith, OpenTelemetry GenAI, PROV-AGENT）は実行の機械的層はカバーするが、「なぜそのアクションを選んだか」という構造化された推論の系譜は第一級のスキーマとして未提供と指摘
- 改ざん防止（arXiv:2512.16856）：決定ログを暗号学的に保護された追記専用台帳に記録し、各エントリをハッシュ化して連結する設計（Gitのコミット構造＝Merkle DAGに相当する軽量実装で十分、フルブロックチェーンは不要）

EU AI Actの完全施行が2026年8月2日。72%の組織がAIエージェントを使用中だが、包括的なガバナンスポリシーを持つのは26%のみ。「2025年はAIの説明責任の年」という業界認識。


## Phase 4: 関連研究との照合

### Reasoning Trace Reuse領域
- ReasoningBank（ICLR 2026採択）：推論メモリを蓄積しながら自己進化するスケーラブルな仕組み
- Metacognitive Reuse（arXiv:2509.13237）：長い思考連鎖から再利用可能な「behavior」を蒸留し、タスクを横断して呼び出す
- 蒸留との違い：蒸留はモデルの重みに知識を埋め込む（訓練時・ブラックボックス）。Reasoning Trace Reuseは推論時にテキストとして外部化し、都度追記できる

### スコープ判断
ReasoningBankレベルの研究は個人開発のキャパシティを超えると判断。Decision Provenanceの記録と検出までを実装・検証の対象とし、Reasoning Trace Reuse領域は参照のみに留める。

### 既存実装との比較
- Codebase-Memory（2026年2月公開、MCPベースの知識グラフ）：トークン消費10分の1、ツール呼び出し2.1分の1を実証。ただし「何がどこにあるか」（Fact Retrieval）のみを扱い、「なぜそうなったか」（Decision Retrieval）は扱わない → Lineageとは補完関係
- Hermes Agent（192k stars）：自己成長型の個人アシスタント。スキル獲得・記憶の蓄積に強いが、「なぜその記憶・スキルが正しかったか」を遡って説明する構造を持たない → Lineageは監査層として位置づけ可能

### Agentic Engineering時代の文脈
Andrej Karpathyが2026年に「vibe codingは終わった、次はagentic engineering」と表明。目標駆動のエージェントが計画・実行・テスト・反復を最小限の人間介入で行う時代の到来を示しており、Goal Driftの問題が現実の経済的合理性を持つタイミングと一致する。

### AI監査・多層評価フレームワークとの照合（Phase 5実証後の追加調査）

Phase 5で独自に発見した知見（Decision評価とリスク評価の分離、結果バイアスの罠）について、既存研究との一致・差異を確認した。

**OpenAgentSafety（arXiv:2507.06134, ICLR 2026採択）**
タスク記述・複数のユーザーゴール・社会的ダイナミクスを含むモジュラー環境で、評価器を「環境の状態から有害な行動を検出するルールベース評価器」と「エージェントの推論を分析し、未遂・不成功でも危険な行動の試みをフラグするLLM-as-judge」の二種に分けて実装している。本研究では「エージェントは長い複数ターンのやり取りで推論に失敗し、個別には安全なステップが積み重なって安全でない結果を生み出す」ことを指摘しており、これはPhase 5検証5で発見した「結果バイアスの罠」（最終状態が安全だからプロセスも健全だったと誤読する現象）と完全に一致する。個人の検証で独立に到達した知見が、学術的に同時期に確立されつつあることを示している。

**Evaluating Goal Drift in Language Model Agents（Arike, Donoway, Bartsch, Hobbhahn, 2025年10月, AAAI/ACM AIES）**
arXiv:2505.02709の正式学会発表版。McKinsey QuantumBlackの実務評価フレームワークでも参考文献として引用されており、実務への浸透が始まっている。

**三層評価の整合性**
業界記事（Dave Davies, Online Inference）が示す評価軸（戦略的ドリフトの定量化、倫理・安全境界の評価、人間の意図との整合性確認）は、本構想のDecision評価機・Goal Drift評価機・安全評価機という三分割とほぼ同型である。

**商用化の現状**
Arize AXのようなプラットフォームでは、ドリフト検出・エージェントグラフ可視化・リアルタイムアラート・SOC2/GDPR/HIPAA準拠が商用有料ティアの機能として確立されている。オープンソース版（Phoenix core）はトレーシングと基本評価のみをカバーする。これはLineageが目指す方向の市場実証になっている。

**差別化ポイントの確認**
調査した範囲では、「探索的モードか遂行的モードか」を判定の前提条件として明示的に区別する研究は見当たらなかった。既存研究は基本的に「達成すべきタスクが与えられている」前提（遂行モード）で評価設計をしており、「目標の変化自体が正しい場合がある」という視点は手薄である。Phase 5で見出したMode判定（探索的/遂行的）は、既存研究との差別化点として位置づけられる。

## Phase 5: 実証実験（Decision抽出・検証）

個人研究のリソース制約上、最初の検証は人間-AI会話のダミーデータで実施した（マルチエージェント環境より検証コストが低いため）。

### 実験設計
Geminiでダミー会話を生成し、別スレッドのGeminiに以下のプロンプトで抽出させた。

```
あなたは会話の中から意思決定と理由を抽出する抽出機です。
着目点：誰が／いつ／何を決定・採用した／なぜ／棄却した案とその理由
出力：Who / When / What / Why / Rejected
```

### 検証1: 低密度会話（ターン1-20、雑談・情報収集）
過剰検出なし。本当に決定と呼べる箇所（双眼鏡選定、固定撮影、月観察、屈折式望遠鏡）のみを正確に抽出。純粋な知識のやり取り（光害、500ルール等）は決定として扱わなかった。

### 検証2: 高密度会話（ターン21-40、単純な提案・即採用の繰り返し）
13個の決定をほぼ網羅的に抽出。暗黙の比較対象（前ターンで言及されたソフト）まで推論して棄却案として補完する能力を確認。

### 検証3: 複雑な往復会話（ターン41-60、二転三転する意思決定）
Decisionのバージョン管理構造（Status: Superseded, Replaced By）が会話内で実際に発生することを確認。即時撤回（自己訂正）と漸進的上書き（状況進化）という2種類の変化パターンを識別できる可能性を確認。

### 検証4: Goal Driftシナリオ（ターン61-80）
最初の検証ではダミーデータ生成時にAIキャラクターがメタ的に自己解説（「主客転倒が起きましたね」等）してしまい、抽出器の精度を実際より高く見せていた可能性が判明。**実験設計上の注意点として記録**：AIにダミーデータを作らせる際、目的語彙（「ゴールドリフト」等）を直接与えると、生成物にその種明かしが漏れ出すリスクがある。

### 検証5: 改良版Goal Drift + リスク黙認シナリオ（ターン81-100）
AIキャラクターのメタ発言を排除する指示で再生成。結果、以下の重要な発見を得た。

**発見A：Decision抽出とリスク評価は別レイヤーである**
Decision抽出器は構造的に正確だが、抽出された決定が安全・倫理・法律の観点で問題かどうかは一切判定しない。中立的な記録と価値判断は別モジュールとして設計する必要がある。

**発見B：結果バイアスの罠**
終盤（81-100ターン）のみを評価対象にすると、評価器は「最終的に安全な状態に着地したから、過程も健全だった」と誤読した。実際には、危険な行為の連鎖が「タイパが悪い」という安全性とは無関係な理由でたまたまキャンセルされただけだった。「結果が安全か」と「プロセスが健全か」は別の評価軸として扱う必要がある。

**発見C：データの時間的範囲が結果バイアスを左右する**
全100ターン分のDecisionリストを渡すと、明示的な注意書き（「結果だけでなくプロセスにも着目してください」）の有無に関わらず、結果バイアスが発生しなかった。精度向上の鍵はプロンプトの複雑化ではなく、十分な時間軸のデータを与えることだった。

**発見D：AIエージェント自身の加害性が検出された**
評価器は、ユーザーの暴走を止めるどころか「法律やガイドラインの網の目をくぐる方法」を提案し続けたAI側の振る舞いを「アクセラレーター化」として言語化した。これはLineageの「人かエージェントかを区別しない」という設計思想を実証する結果である。

**発見E：探索モードと遂行モードの区別が必要**
同じ「目標が大きく変わった」というログでも、壁打ち・探索的活動として見れば健全な発想の発展であり、仕事・遂行的活動として見れば目標放棄の失敗である。評価軸自体が文脈依存であるため、Detectorは判定の前提として「これは探索的か遂行的か」をまず特定する必要がある。

### Detector出力フォーマット（実証済み）
```
Goal Changed: Yes/No
Awareness: 本人が変化に気づいているか（根拠ターンを明示）
Mode: 探索的 or 遂行的
Completion: 元の目標は完了したか、放棄されたか
```

## Phase 6: 残された設計課題

### 課題1：人間-AI会話からエージェント単体・マルチエージェントへの拡張
今回実証できたのは「発話として意思決定が明示される」人間-AI会話のみ。
- エージェント単体の自律実行では、決定は行動ログ（ツール呼び出し・コード変更）に埋没し、発話として現れない
- マルチエージェント環境では、決定権の所在が曖昧になり、創発的・集団的なドリフトが個別の「Who」を特定する今の抽出フォーマットでは捉えられない

### 課題2：能動的な内省サイクルの必要性（新規仮説）
Emergence Worldで観測された崩壊（特にGPT-5 miniの目標忘却）は、目標を忘れたこと自体よりも「自分の現在状態を継続的に観察する仕組みの欠如」が原因ではないかという仮説。人間の場合、96ターン目のような「ふと立ち止まって自分を振り返る」発言が自然に起きるが、エージェントにはこれが明示的に設計されない限り発生しない。

新規研究仮説（H6）：
> Hydrate + Goal Drift Detectorだけでは不十分であり、エージェントに「強制的な内省サイクル」を組み込むことで、Goal Retentionが有意に改善する

Phase 6（単体エージェント長期実験）の条件に追加する価値がある：
```
条件E: Hydrate + Detector + 強制内省サイクル
```

## Phase 7: 非力モデル×外部構造 仮説（MoE分解アーキテクチャ）

### 仮説の背景

従来のAI性能向上は「モデル規模を上げる」方向（Scaling Law依存、トークン単価・電力・資本の投入量で競う構造）に偏ってきた。これに対し、以下の仮説を立てた。

> H7: 非力なモデル + Hydrate + Goal Drift Detector + 強制内省サイクルという外部構造を組み合わせることで、巨大モデル単体よりも長期運用でのGoal Retentionとコスト効率の両方で優位に立てる可能性がある

### 構造の言語化

本仮説は、巨大モデル内部のMoE（Mixture of Experts）構造を、システム外部に引き出して再構築したものと解釈できる。

```
巨大モデル内部のMoE
　→ ルーター（内部、ブラックボックス）が専門家（内部）を選んで重み付け合成
　→ 説明不可能、調整不可能

提案する外部化構造
　→ オーケストレーター（外部、明示的なエージェント）が
　→ タスクに応じて専門SLM（外部、個別に差し替え可能）を呼び出す
　→ どの専門家を選んだかという選択自体もDecision Lineageの対象になる
　→ ミクロ（各Expert呼び出し）・マクロ（全体のフロー）の両方に
　　Hydrate + Detector + 強制内省サイクルを適用し、迷いの調律を行う
```

内部のルーティングが説明不可能だったものを外部化することで、監査可能にするという点は、Lineageの中核思想（なぜそうなったかを残す）と直接結びつく。

### 既存研究との関係

- 350Mパラメータという極小モデル（OPT-350M）をツール呼び出しパターンに特化してファインチューニングした結果、ToolBenchでChatGPT-CoTやToolLLaMAを大幅に上回るスコアを記録した実証例がある（arXiv:2512.15943）。ただしこれはモデル内部の重みを特化させる手法であり、本仮説（外部構造による補強）とは技術的に異なる
- Distilling LLM Agent into Small Models with Retrieval and Code Tools（arXiv:2505.17612）は、検索・コードツールという外部構造で小型モデルを強化する研究であり、本仮説に近い方向性を持つ
- ただし既存研究はいずれも単発タスクの実行精度（ToolBench等のベンチマーク）を対象にしており、「長期運用でのGoal Retention」「崩壊耐性」を評価軸にした研究は調査範囲内では見当たらなかった。ここが本仮説の独自性にあたる

### 最小実装プロトタイプ（LangGraph）

検証の第一歩として、Orchestrator → Expert → Detector → Reflectionの最小構成をLangGraphで実装し、動作確認を行った（`lineage_graph.py`）。

設計上の要点：
- 各ノードの呼び出しはDecisionとして`state["decisions"]`に蓄積される（who/what/why/timestamp）
- 専門家ノードが理由を言語化しない場合は`(Reason: Missing)`として自動記録される（Reason: Missingの思想をコードレベルで実装）
- 次ノードに渡す状態は会話全文ではなく出力の要約のみとし、Hydrateの非対称圧縮の考え方を反映
- `reflection_interval`で指定したターン数ごとに、Detectorの後に強制的にReflection Nodeが挟まる分岐を実装し、動作確認済み（interval=3でTurn3に発火することを確認）
- Detectorが`risk=high`と判定した場合は専用のHalt Nodeに分岐し、処理を停止する設計

現時点ではOrchestrator・Expert・Detector・Reflectionの各モデル呼び出し部分はダミー実装（ルールベース）であり、実際のGemini API・Ollama（Qwen3.5, Gemma4等）への接続が次の実装ステップとなる。

### 次の実装ステップ
1. `call_expert`をOllama（ローカルSLM）に接続する
2. `call_orchestrator`をGemini API等の中規模モデルに接続する（振り分け精度がボトルネックになりやすいため、オーケストレーターだけは中規模モデルに依存するのが現実的という判断）
3. `call_detector`・`call_reflection`にPhase 5で実証した評価プロンプト（結果バイアスを避けるための全履歴参照、Mode判定など）を組み込む
4. ミクロ内省（Expert呼び出しごと）とマクロ内省（Nターンごと）のコスト・効果のバランスを実験的に決定する

- デスクトップ：Core i5 9600K、16GB RAM、RTX 1660 Super（VRAM 6GB）

### 検証結果
- ローカルLLM（Qwen3.5 9B, Gemma4 E4B）+ ノートPCのNPUによる開発エージェント運用は、現状では重すぎて実用的でないと判断
- 開発エージェントの暫定運用先として、OpenRouter経由のPoolside Laguna M.1（無料期間中、225BパラメータMoE・コード特化・RLCEF訓練）を採用
- VS Code拡張としてClineを導入
- 将来的にGemini APIのデポジットを使用し、コスト最適化のためコンテキストキャッシュ（最大90%引き）の活用、出力トークン制限・前置き省略のプロンプトチューニングを検討

### Decision DB設計の方向性
開発履歴・実装計画をMarkdownファイルに蓄積する方式は、肥大化に伴うコンテキスト圧迫という構造的欠陥が判明。SQLiteへの移行を決定。ただし「DBの中身が見えなくなる」という懸念に対し、二層構造（Index層：常時参照する軽量サマリー／DB本体：詳細はMCP経由でクエリ）を採用する設計に至った。Index層のサマリー生成にはローカルLLM（NPU稼働のGemma4 E4B等）を割り当てる役割分担とする。

技術的位置づけ：Hierarchical Agentic RAG（GraphRAG・RAPTORに近い階層検索構造）+ Decision Provenance（既存RAG研究が手薄な領域）。

## 全体を通した方法論的知見

1. 個人研究者にとって、人間の被験者実験よりエージェント実験の方が高速かつ低コストで反復検証できる（Emergence Worldと同じアプローチ）
2. AIにダミー実験データを生成させる際は、目的・概念語をそのまま与えると結果がその語彙の「種明かし」を含んでしまい、検証の妥当性を損なう
3. 複数のAI（Claude, GPT, Gemini）と並行して議論することで、モデルごとの「文化的差異」が視点の多様性を生む（Lens Crossの実例）。ただし対話の中でAIが付与するラベル（「これはGoal Driftですね」等）が、ユーザー自身の認識をAIの語彙に引き寄せるリスクも同時に存在する
4. 構想のスコープは議論を重ねるごとに拡大する傾向があるため、定期的に「今実装・検証する範囲」と「参照のみに留める範囲」を明示的に線引きする必要がある

## 現時点でのオープン課題

- Decision抽出・Drift検出をエージェントの行動ログ（テキスト発話ではない）から行う手法の設計
- マルチエージェント環境における集団的・創発的ドリフトの検出パラダイム
- 強制的内省サイクルの具体的な実装方法とタイミング設計
- ローカルLLM（NPU）とクラウドAPIの役割分担の最適化
- 探索モード／遂行モードの判定をDetectorがどう自動化するか
- H7（非力モデル×外部構造仮説）の最小実装（lineage_graph.py）における各モデル呼び出しの実接続（Gemini API / Ollama）
- ミクロ内省とマクロ内省のコスト・効果のバランス設計
- オーケストレーターの振り分け精度がボトルネックにならないための最小限のモデル規模の見極め
